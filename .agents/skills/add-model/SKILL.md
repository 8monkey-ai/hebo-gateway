# Add Model or Provider

The model catalog is **not** maintained in this repo. It comes from [models.dev](https://models.dev), which is also the source of truth for provider-native model IDs:

- At runtime the gateway loads `https://models.dev/api.json` once (first request) and converts it with `fromModelsDev` (`src/models/models-dev.ts`), for the labs that are imported.
- If that fails it falls back to the snapshots bundled with the release, `src/models/<lab>/models-dev.json`, generated by `bun run models:sync`. Run it and commit the result; releases bundle whatever is committed. Never edit the snapshots by hand: they are converter output, so fix the converter (or the adapter's `pick` hook) instead and re-sync. `bun run models:check` lists how the committed snapshots differ from the live data.
- Each lab module (`src/models/<lab>/presets.ts`) is the only place that names its lab: `registerModels({ namespace, provider, host, snapshot, extras })` registers it, `declare module "../types.ts"` adds its snapshot IDs to `CanonicalModelId`, and `defineModelFamily(lab, …)` exports its model families. The converter and `models:sync` read the registered labs.

So a new model usually needs **no change here**. Changes are needed when:

- models.dev does not list the model, or one of its providers (yet): add a lab extra, and open an upstream PR,
- the model needs request translation (model or provider middleware),
- the model does not fit its family's `version` pattern or a named group,
- a new lab or provider is added.

Fix wrong data upstream on models.dev. Extras only fill gaps: a missing model, or a provider missing from a model models.dev lists. Once models.dev lists the model (or that provider), its data is used instead, so there is no way to override upstream data.

## Step 1: Find the Model on models.dev

The full `api.json` (~7 MB) is `{ [provider]: { models: { [nativeId]: {...} } } }`. Grep instead of loading it:

```bash
# Every listing of a model, with its provider-native ID and canonical ID
curl -s 'https://models.dev/api.json' | jq -c 'to_entries[] | .key as $p | .value.models | to_entries[]
  | select((.value.canonical_model_id // .key) | test("<SEARCH_TERM>")) | {provider: $p, id: .key, canonical: .value.canonical_model_id, status: .value.status, type: .value.type, npm: .value.provider.npm}'
```

Relevant fields: `canonical_model_id` (`<lab>/<model>`), `family`, `status` (`deprecated` listings are kept but used only when a provider has no current one, and mark the model `deprecated` when every provider only has deprecated ones; `deprecated` / `alpha` / `beta` models are kept out of `latest`), `type` (`embedding` / `transcription`; image, video, speech, ... are ignored), `provider.npm` (listings served through an SDK the adapter does not speak are ignored, see `registerModelsDevHosts`), `release_date`, `knowledge`, `limit.context`, `modalities`, `attachment`, `reasoning`, `tool_call`, `structured_output`, `temperature`.

Listings whose native ID is not a plain ID (`[\w.:/@-]`, no `..`, at most 200 characters), or a Bedrock ARN / unknown inference profile prefix, are skipped: upstream data is untrusted.

The canonical ID used by the gateway is the models.dev one (`canonical_model_id`, or `<lab>/<id>` for first-party listings without it), e.g. `anthropic/claude-sonnet-4-6`, `moonshotai/kimi-k3`, `zhipuai/glm-5.3`, `minimax/MiniMax-M3`. Do not invent IDs.

Then refresh the snapshots and check the entry:

```bash
bun run models:sync
jq '."<canonical-id>"' src/models/<lab>/models-dev.json
```

`providers` maps every gateway provider models.dev lists it on to its native ID, lab first. When a provider lists several IDs for a model, `fromModelsDev` picks one:

- **Bedrock**: Converse first (`profile: "optional"` when inference profiles are listed too, `"required"` when only profiles are), then Mantle (`route: "mantle"`). The adapter applies the configured profile; native IDs never carry routing syntax. Limits and reasoning come from the plain listing, then a regional profile, then GovCloud.
- **Others**: the ID named like the model, then the shortest; Fireworks routers last.

## Step 2: Fill Gaps (only if models.dev lacks the model or a provider)

Add the entry to the `extras` of `registerModels` in `src/models/<lab>/presets.ts` (see `microsoft`, `voyage`, `cohere`). Extras use the snapshot's shape: `providers` maps each provider serving it, in routing order, to its spec. Leave the spec empty (`{}`) when the provider's derived ID (usually the canonical ID without namespace) is what it serves; set `id` otherwise (e.g. `{ deepinfra: { id: "Qwen/Qwen3-Embedding-8B" } }`). Verify the metadata against the lab's docs; keep it minimal rather than speculative.

For a provider missing from a model models.dev lists, the extra only needs that provider (e.g. `cohere/embed-v4.0` on Bedrock); upstream providers keep their data and order, the filled ones come last. The same goes for models models.dev lists on no gateway provider (it rarely lists embedding / transcription models under their lab, e.g. `openai/whisper-1`): the converter keeps them, with no providers, only when the lab's extras name one (`{ providers: { openai: {} } }`). No provider is ever assumed.

## Step 3: Check the Model Family

Families (`src/models/<lab>/presets.ts`) select models by a `version` pattern, resolved when the catalog loads. Patterns and named groups are written without the lab namespace (e.g. `claude-opus-*`):

- `all`: every model matching `version`, plus every named group; `vX` / `vX.Y` / `vX.x`: by the captured version (`-` reads as `.`). Keep embedding / transcription models out of `version` when the lab's version groups never had them (e.g. `gemini`, `qwen`): they are still in `all` through their named group.
- `latest`: the newest stable `release_date` per models.dev `family`.
- Named groups: `*` patterns.

Check the new model lands in the expected groups; adjust the pattern or a named group otherwise, and keep `README.md` (Model Families) in sync.

## Step 4: Check Whether Middlewares Are Needed

Middlewares bridge OpenAI-compatible request parameters to provider-native options. They exist at **two levels** — both must be checked.

### Model-level middlewares (`src/models/<lab>/middleware.ts`)

Registered via `modelMiddlewareMatcher.useForModel()` when the lab module is imported, and matched by canonical model ID patterns. Patterns cover the whole lab (e.g. `anthropic/claude-*`, `deepseek/*`), never single versions: a new model must get the middleware without a code change.

What differs per model comes from its **model spec** (models.dev data per provider: native ID, output limit, reasoning controls), not from its ID. Middleware that needs it reads it with `specOf(model)` (the `model` passed to `transformParams`) and gets the controls with `reasoningControls(spec, FALLBACK)`, where `FALLBACK` describes the lab's current generation (used for models without data). `resolveReasoning` maps the request to what the model takes; the middleware only writes the result in the lab's API shape.

| Category       | When needed                                                                             | Example                                                                                         |
| -------------- | --------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| **Reasoning**  | Model supports extended thinking / chain-of-thought (`reasoning` in `capabilities`).    | `claudeReasoningMiddleware` maps `reasoning.effort` → Anthropic `thinking` / `effort` options   |
| **Dimensions** | Embedding model supports variable output dimensions with a non-standard parameter name. | `voyageDimensionsMiddleware` maps `dimensions` → Voyage `outputDimension`                       |
| **Caching**    | Model supports prompt caching (`cost.cache_read` / `cost.cache_write` on models.dev).   | `claudePromptCachingMiddleware` maps `cache_control` → Anthropic `cacheControl` provider option |

1. A new model of an existing lab usually needs nothing: run `bun run models:sync` and review the reasoning changes it lists.
2. Behaviour models.dev doesn't describe goes in the lab middleware as a list of the **older** models that differ (e.g. explicit caching is `google/gemini-3*` only), so the list never grows. If an old model would need special-casing in otherwise generic logic, prefer dropping it with `exclude` in the lab's `registerModels` (e.g. Claude 4.5).
3. Add or update tests in `src/models/<lab>/middleware.test.ts`, with inline specs.

### Provider-level middlewares (`src/providers/<provider>/middleware.ts`)

Registered via `modelMiddlewareMatcher.useForProvider()` and matched by provider ID.

| Category          | Providers with middleware   | What it does                                                                                                    |
| ----------------- | --------------------------- | --------------------------------------------------------------------------------------------------------------- |
| **Service tiers** | `bedrock`, `vertex`, `groq` | Maps OpenAI `service_tier` values to provider-native equivalents (e.g., `"scale"` → Bedrock `"reserved"`)       |
| **Reasoning**     | `bedrock`, `fireworks`      | Translates reasoning params into provider-native format (e.g., Bedrock `reasoningConfig`, Fireworks `thinking`) |
| **Caching**       | `bedrock`                   | Maps `cache_control` → Bedrock `cachePoint` with provider-specific TTL handling                                 |

Provider-level middleware can read the model spec with `specOf(model)` too (e.g. `bedrockMantleReasoningMiddleware`). Some middlewares filter internally by native model ID (e.g. `bedrockPromptCachingMiddleware` only applies to `nova` and `claude`); update those filters when needed.

## Step 5: New Lab or Provider

- **New lab** (canonical namespace):
  1. Create `src/models/<lab>/presets.ts` (copy an existing one): `registerModels` with the `namespace`, the gateway `provider` the lab runs (omit if none) and its models.dev first-party `host` (only when it differs from the namespace, e.g. `zai` for `zhipuai`), the `declare module` block, and its families. Add `index.ts` and an empty `models-dev.json` (`{}`).
  2. Run `bun run models:sync`: it finds the lab on disk and writes its snapshot.
  3. Add the `./models/<lab>` export to `package.json`. Tests pick the lab up from disk.
- **New provider adapter**: add it to `CANONICAL_PROVIDER_IDS` (`src/providers/types.ts`, in provider preference order). Use the models.dev provider ID as gateway provider ID when possible; otherwise, or when the adapter speaks SDKs besides the models.dev default, call `registerModelsDevHosts` in its `canonical.ts` (see Vertex). Provider-specific models.dev handling stays in the adapter: a `pick` hook chooses among several native IDs and may add spec fields declared with `declare module` on `ModelSpec` (see `src/providers/bedrock/models-dev.ts`, Fireworks routers). Create `src/providers/<provider>/` with a `withCanonicalIdsFor*` adapter (only provider-wide rules: native IDs come from the catalog), add the package export and a case to `src/providers/catalog-ids.test.ts`.

### Canonicalization options reference

```typescript
type CanonicalIdsOptions = {
  providerId: ProviderId; // Gateway provider ID: instances wrapped for it share the catalog's specs
  mapping?: Partial<Record<ModelId, string>>; // Explicit canonical → native IDs, win over the catalog
  nativeId?: (spec: NativeModelSpec) => string; // Native ID for a catalog spec (e.g. Bedrock profiles)
  // Transform for IDs neither `mapping` nor the catalog knows:
  options?: {
    stripNamespace?: boolean; // Remove "lab/" prefix (default: true)
    normalizeDelimiters?: boolean | string[]; // Convert "." → "-" (default: false)
    prefix?: string; // Prepend to transformed ID
    template?: Record<string, string>; // `{key}` substitution, also in `mapping` (never in catalog IDs)
    postfix?: string; // Append to transformed ID
    namespaceSeparator?: "/" | "." | ":"; // Namespace delimiter (default: "/")
  };
};
```

## Step 6: Write Tests

- Native IDs for every bundled model and provider: `src/providers/catalog-ids.test.ts`
- Provider-wide rules: `src/providers/<provider>/canonical.test.ts` (use `loadBundledCatalog` from `test/helpers/catalog.ts`)
- Middleware pattern tests: `src/models/<lab>/middleware.test.ts`
- Conversion changes: `src/models/models-dev.test.ts`; catalog / families: `src/models/catalog.test.ts`

## Step 7: Update README

Update `README.md` when a provider adapter is added (Built-in adapters list), a family or named group changes (Model Families), or catalog behavior changes (Models section).
